## 0. 问题描述与验收口径

**问题**：`decode_bgr()` 先按原始分辨率完整解码再降采样，`encode_image_b64()` 调 `load_image_color(path)` 时未传 `max_long_side`（阶段 2 的 `ThreadPoolExecutor` 并发全分辨率解码）；全仓库 `MAX_IMAGE_PIXELS` 检索为 0 条，Pillow 默认的 89M 告警 / 178M 抛错双阈值未被收紧，89M~178M 的灰色地带可合法分配数百 MB；`np.array(img)[:, :, ::-1].copy()` 又额外产生一份全量拷贝。

**修复后验收口径**（逐条可判定）：

1. 单张图解码前按其头部尺寸预检像素数，超过 `MAX_IMAGE_PIXELS` 即抛 `ImageReadError`，**绝不分配像素缓冲**（`tracemalloc` 实测无百 MB 级分配）。
2. `Image.MAX_IMAGE_PIXELS` 在 `flashgaze.utils.image_io` 导入期被显式收紧为项目常量；Pillow 抛出的 `DecompressionBombError` 统一转为 `ImageReadError`。
3. 超限图在 CV 阶段即降级为 `CVResult(error=...)` → `ImageScore.error`，**不进入** VLM 阶段 2 线程池；其余图正常评分，CLI 退出码与报告结构不变。
4. ~~`decode_bgr` 的全量数组分配由 2 份降为 1 份~~ —— **经实测不成立，该改动已撤销**（详见 §八）：Pillow 12.2 的 `__array_interface__` 返回 `tobytes()` 产出的 bytes 副本，`np.asarray` 与 `np.array` 的解码峰值完全等同（5000×5000 实测 143.28 vs 143.20 MiB）。改为新增护栏用例 `test_asarray_gives_no_memory_benefit_over_array` 钉死该事实，避免日后重复该无效「优化」。解码像素**逐位不变**由 `test_decode_bgr_returns_owned_contiguous_array` 保证。
5. 逃生舱 `FLASHGAZE_MAX_IMAGE_PIXELS` 可上调阈值；置 `0` 关闭项目上限、沿用 Pillow 旧行为。
6. 正常图（512×512 / 4K / 12MP 手机图）**不被误伤**（反例）。

### 1.5 历史约束与注意事项

- **中文路径**：工作区 `d:/Qoder项目/SaiTu skill`。`execute_command` 生成的 .ps1 会把命令行中文按 GBK 误解析 → `cd`/路径命令失败；统一用 `python -m ...` / `python -c "..."`，不用 `cd` 拼接中文路径。
- **`tests/test_cli_e2e.py` 本机全红是环境假阳性**（子进程 stdout 按 GBK 解码），全量回归统一带 `PYTHONIOENCODING=utf-8`。
- **判定 lint 是否新增问题不能看总数**：`ruff check` 无存量；`ruff format --check` 有 38 文件存量漂移（本地 ruff 0.16.4）。新增代码写成「单行 ≤100 字符」可同时兼容新旧 formatter；判定用 `ruff check --diff <改动文件>` 与 `ruff format --diff` 看 hunk 行号是否落在新增区间。
- **mypy 基线 0 错误（76 源文件）**：任何 1 条都是新增，必须修掉。
- **解码契约**：所有解码一律走 Pillow（cv2.imread 在 Windows Unicode 路径返回 None，双解码器会让像素差 ±1 破坏 `--no-vlm` 逐位可复现性），cv2 仅用于色彩转换/缩放。
- **算子顺序契约**：`cv_engine._load_eval_images` docstring 明示「gray 先转换后降采样、color 直接降采样」的顺序不可变，否则大图评分会漂移 ±1。
- **日志约定**：批量评分避免逐图刷屏（`_heif_warned`、`_noise_warn_logged` 均为只提示一次）。
- **进程级副作用约定**：`_ensure_heif_support` docstring 明示「作为库被导入时应避免副作用」——本次导入期收紧 `Image.MAX_IMAGE_PIXELS` 必须同样明示并提供关闭开关。
- 非 git 仓库（`ocr` 无法走 diff 模式）。

## 四、错误处理

| 分支 | 处理 | 级别 | 用户可见文案 |
|---|---|---|---|
| 头部尺寸超上限（`MAX < px ≤ 2×MAX`） | 抛 `ImageReadError` | **不逐图打 WARNING** | `图片尺寸超限：10000×10000（100000000 像素）超过上限 64000000 像素，已跳过以避免解压炸弹导致 OOM；如需处理请设置 FLASHGAZE_MAX_IMAGE_PIXELS=<更大值>（置 0 关闭本上限）` |
| Pillow 抛 `DecompressionBombError`（`px > 2×MAX`） | 捕获后转 `ImageReadError` | 同上 | `图片尺寸超限（Pillow 解压炸弹保护），已跳过: <原异常>` |
| 环境变量 `FLASHGAZE_MAX_IMAGE_PIXELS` 非法（非整数） | 记 warning 并回退默认 | `WARNING` | `<name>=<raw> 非法，回退默认 <default>` |
| 环境变量置 `0` / 负数 | 关闭项目上限，沿用 Pillow 自带阈值 | 无 | — |
| 64M~128M 区间 Pillow 额外打印的 `DecompressionBombWarning` | 不抑制（`warnings.catch_warnings` 在阶段 2 线程池下有竞态） | 库告警 | 文档与 docstring 明示「`ImageReadError` 才是权威信号」 |
| 超限图的最终去向 | `CVResult.error` → `ImageScore.error`；不进 VLM 阶段 2；WebUI 画廊跳过 | — | JSON/CSV 报告的 `error` 字段 |

**日志输出位置**：`flashgaze.utils.image_io` 的 `logger`（仅环境变量非法时一条 WARNING）；超限原因通过异常消息进入 `ImageScore.error`，在 JSON/CSV/WebUI 中程序化可见，不刷屏。

## 七、影响面与兼容性说明

**受影响的调用方**：全部走 `decode_bgr` / `load_image_*` / `encode_image_b64` 的调用方（见 §1.3 表）。它们**已在捕获 `ImageReadError` 或 `Exception`**，因此**无需任何调用方改动**，不抛栈、不中断批次。

**是否构成破坏性变更**：**是（行为变更，非签名变更）**。原先「可能 OOM 但勉强能解」的 >6400 万像素图，现在改为降级为 `error` 占位。

**过渡方案**：
1. 逃生舱环境变量 `FLASHGAZE_MAX_IMAGE_PIXELS=<更大值>`；
2. 置 `0` 完全关闭项目上限，恢复到修复前的 Pillow 默认行为（89M 告警 / 178M 抛错）；
3. README 环境变量表与能力边界段落同步声明该行为与恢复方式。

**不受影响**：CV 评分数值（零像素漂移）、CLI 退出码、JSON/CSV 报告结构、MCP 六字段 Schema、WebUI 输出契约、EXIF 写入、清理护栏。

**因本次改动而合理失效的旧用例**：**无**（预计）。若 T6 出现失效，须在此逐一列出失效原因与替代用例，不得静默删除或弱化断言。

## 八、技术取舍记录（未采用项）

**未采用 `Image.draft()` 渐进/分块缩放**（审查报告修复方向的可选项 A）：
- 理由一：draft 只对 JPEG 生效，且会改变解码像素 → 改变 VLM 请求体输入；若误用于 CV 路径会破坏 `--no-vlm` 的逐位可复现性（`tests/test_reproducibility.py` 是硬约束，`cv_engine._load_eval_images` docstring 明示算子顺序不可变）。
- 理由二：审查报告 §8.2 第 12 行的验收口径只要求「超限降级为 error 占位 + `MAX_IMAGE_PIXELS` 被显式收紧」，即可选项 B。
- 残余风险与收敛效果：阶段 2 单线程峰值已被硬上限封顶为 `64M × 3B ≈ 192MB`（且超限图根本不进入阶段 2），相比改动前的「无上限」收敛一个数量级且可预测。

**未采用 `np.asarray` 消除二次拷贝**（审查报告修复方向的第 4 项）——**先实施、实测无收益后撤销**：

- 预想：`np.array(img)[:, :, ::-1].copy()` 先复制一份全量 RGB、再复制一份 BGR；换成零拷贝的 `np.asarray` 可省掉前者。
- 实测（Pillow 12.2.0 / numpy 2.2.6，5000×5000 RGB）：
  - `np.asarray(im)` 结果的 `base` 是 **`bytes`**、`OWNDATA=False`、`WRITEABLE=False`。
  - 根因：Pillow 的 `Image.__array_interface__` 返回的是 `tobytes()` 产出的 **bytes 副本**，并非指向 Pillow 内部缓冲的视图；故 `np.asarray` 只是"不拥有"这份副本，并无省内存效果。
  - 整条表达式的 `tracemalloc` 峰值：`np.asarray` 路径 **143.28 MiB** vs `np.array` 路径 **143.20 MiB** —— 差值 <0.1 MiB，等同。
- 处置：撤销该改动，`decode_bgr` 维持 `np.array` 原写法，并在代码注释与用例 `test_asarray_gives_no_memory_benefit_over_array` 中记录实测数据与根因，防止日后重复。
- 教训：此前用小图只验证了 `OWNDATA=False` 这一**代理标志**就下了结论，未验证真实内存行为；判定此类优化必须以峰值实测为准。

**遗留观察（未修，不影响本次验收）**：64M~128M 区间的图，Pillow 会在 `Image.open` 时额外打印一条 `DecompressionBombWarning`（随后立刻被 `ImageReadError` 取代）。阶段 2 是线程池，`warnings.catch_warnings()` 改全局状态有竞态，故不抑制；文档与 docstring 已明示 `ImageReadError` 才是权威信号。
